# OCP-0001: Open Context Protocol
**Status:** Draft — RFC v0.1
**Editor:** Rajesh Banoth
**Layered on:** Model Context Protocol (MCP)
**License:** CC-BY 4.0 (specification text) · Apache-2.0 (reference implementations)

---

## Abstract

The Open Context Protocol (OCP) defines how AI agents share retrievable context, persistent state, and invalidation events across models, frameworks, and organizations. OCP is a profile layered on top of the Model Context Protocol (MCP): every OCP server is an MCP server, and every OCP client is an MCP client. Where MCP defines the transport, capability negotiation, and tool invocation primitives, OCP defines the canonical tool surface, data shapes, scope semantics, and event contracts that make context portable between agents.

The goal is a single, model-neutral, runtime-neutral protocol that closed AI runtimes can plug into and that regulated industries can deploy under their own governance — without rebuilding the memory and coordination layer from scratch for each agent stack.

## Status

This document is RFC v0.1. It is intended to anchor the first reference implementations and gather implementer feedback before v1.0. Breaking changes between v0.x releases are expected. Implementations targeting this version MUST advertise `protocol_version: "ocp/0.1"` in their MCP server descriptor.

## 1. Terminology

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119.

- **Server**: an MCP server that implements the OCP tool surface defined in §4.
- **Client**: any MCP client (IDE extension, CLI, agent runtime, framework) that calls OCP tools.
- **Agent**: a logical caller of OCP tools, identified by an `agent_id`. Multiple agents MAY share a single client process.
- **Workspace**: the top-level container of indexed content (a repository, knowledge base, document set, ticket archive). Identified by a `workspace_id`.
- **Session**: a bounded unit of coordinated work, typically spanning multiple agent invocations and possibly multiple agents. Identified by a `session_id`.
- **Chunk**: an addressable unit of retrievable content with stable identity, source attribution, and an embedding.
- **State entry**: a typed key-value pair scoped to a workspace, session, or agent.
- **Scope**: one of `agent`, `session`, `global` — see §5.

---

## 2. Relation to MCP

OCP does not redefine transport, authentication, capability negotiation, or tool-call mechanics. Those are MCP's responsibility. OCP defines:

- A canonical set of tool names and JSON Schemas (§4)
- A canonical data model for chunks, state, and events (§3)
- Scope resolution semantics (§5)
- Invalidation propagation contract (§6)
- An events subscription channel layered on MCP notifications (§7)

A conformant OCP server MUST implement all tools marked REQUIRED in §4. It MAY implement OPTIONAL tools. It MUST advertise the OCP profile in its MCP server descriptor:

```json
{
  "name": "example-context-server",
  "version": "1.2.0",
  "profiles": ["ocp/0.1"],
  "conformance": "core+coordination"
}
```

OCP intentionally does not require MCP extensions. A server that speaks vanilla MCP plus the tool surface in §4 is a conformant OCP server.

## 3. Core Data Model

### 3.1 Chunk

A chunk is the fundamental unit of retrievable context.

```json
{
  "id": "string",
  "workspace_id": "string",
  "source": {
    "uri": "string",
    "range": {
      "start_byte": "integer",
      "end_byte": "integer",
      "start_line": "integer",
      "end_line": "integer"
    },
    "content_hash": "string"
  },
  "kind": "string",
  "language": "string",
  "symbol": "string",
  "content": "string",
  "metadata": { },
  "version": "integer"
}
```

**Field requirements:**

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Stable across reindex if content unchanged. See §3.4. |
| `workspace_id` | yes | |
| `source.uri` | yes | e.g. `file://src/auth/jwt.ts`, `doc://policy-handbook/chapter-3` |
| `source.range` | for files | OPTIONAL for non-positional sources |
| `source.content_hash` | yes | SHA-256 of the chunk's raw content bytes, hex-encoded |
| `kind` | yes | e.g. `function`, `class`, `section`, `paragraph` |
| `language` | no | ISO-like identifier, e.g. `typescript`, `python`, `markdown` |
| `symbol` | no | e.g. `verifyJWT` |
| `content` | yes | The retrievable text |
| `metadata` | no | Server-defined; clients MUST tolerate unknown fields |
| `version` | yes | Monotonic integer; increments on content change |

### 3.2 State entry

```json
{
  "key": "string",
  "value": "any",
  "scope": "agent | session | global",
  "workspace_id": "string",
  "session_id": "string",
  "agent_id": "string",
  "ttl_seconds": "integer",
  "updated_at": "string",
  "version": "integer"
}
```

### 3.3 Identity rules

- **`workspace_id`** is opaque and server-issued. Servers SHOULD derive it deterministically from a client-supplied root.
- **`session_id`** is either client-generated (UUIDv4 RECOMMENDED) or server-issued. The first OCP call that references a previously unseen `session_id` MUST cause the server to materialise that session — servers MUST NOT reject an unknown `session_id` in `state.set` or `session.handoff` as long as it is well-formed.
- **`agent_id`** is client-generated. `agent`-scoped state does NOT require `workspace_id`; agents exist independently of any single workspace.

> **S2 — agent scope clarification:** `workspace_id` is REQUIRED for `session` and `global` scope only. `agent` scope intentionally omits this requirement because agent identity transcends any individual workspace. To exchange state between agents within a session, callers MUST use `session.handoff` (which writes to `agent` scope internally) or promote the entry to `session` scope explicitly.

### 3.4 Chunk ID stability

```
chunk_id = base32( sha256(workspace_id || source.uri || range_repr || content_hash) )[:24]
```

Where `range_repr` is the UTF-8 encoding of `"{start_line}:{end_line}"` for positional sources, or the empty string for non-positional sources. Fields are concatenated with a NUL byte (`\x00`) as separator. All strings are UTF-8 encoded before hashing. Implementers MUST use this exact serialisation to ensure cross-server chunk ID stability.

> **S4 — range encoding rationale:** An earlier draft left `source.range` serialisation unspecified. This is now normative to guarantee that two independent implementations produce the same `chunk_id` for the same content, enabling agents to share chunk references across servers.

### 4.3 State (REQUIRED) — clarifications

`state.delete` with `if_version`:
- If `if_version` is supplied and the entry's current version does not match, the server MUST return error `CONFLICT` and MUST NOT delete the entry. (S1 — this was previously underspecified; returning `{deleted: false}` is incorrect.)

`state.set` optimistic concurrency:
- `if_version: 0` means "write only if the key does not yet exist". Servers MUST treat `if_version=0` as a valid check (current version = 0 ⟺ entry absent), not as a falsy no-op.

---

## 5. Scope Model

Resolution order for `state.get` without explicit scope: `agent → session → global`

---

## 6. Invalidation Contract

Chunks MUST be marked invalid on source modification, explicit invalidation call, or content_hash mismatch during reindex.

---

## 7. Events

Events ride MCP notifications. See event types: `chunk.invalidated`, `chunk.indexed`, `state.changed`, `session.handoff`, `session.closed`, `index.progress`.

---

## 8. Security Considerations

Workspace isolation, scope isolation, and identity confidentiality are required. Authentication is delegated to MCP.

---

## 9. Versioning

Protocol version: `ocp/<major>.<minor>`. Breaking changes require major version bump.

---

## 10. Conformance Levels

- **`core`**: Workspace + Retrieval + State + Scope + Invalidation
- **`core+coordination`**: Core + Session coordination tools
- **`full`**: Core + coordination + Events + §8 enforcement
